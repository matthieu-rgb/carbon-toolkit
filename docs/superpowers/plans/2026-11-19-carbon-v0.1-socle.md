# CARBON v0.1 — Socle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer le socle CARBON : un cœur Python (contrat de résultat structuré, registre d'outils, journal d'audit, garde-fou destructif) et une couche CAN sur `python-can`, pilotés par une CLI, le tout empaqueté en image Docker multi-arch — critère : cycle CAN complet (sniff → dump → replay → inject) sur bus virtuel/`vcan0` sans matériel.

**Architecture :** Un paquet Python unique `carbon`. Le **cœur** définit un contrat uniforme (`ToolResult`), une classe de base d'adaptateur + registre, un journal append-only et un garde-fou de confirmation ; tout outil s'y branche. La **couche CAN** encapsule `python-can` (interface `virtual` pour les tests sans root, `socketcan`/`vcan0` à l'exécution). La **CLI** résout un outil dans le registre, applique le garde-fou, l'exécute, journalise. Rien dans le cœur ne connaît le CAN ; rien dans les outils ne connaît la CLI (règle d'or du design).

**Tech Stack :** Python ≥ 3.11, `python-can`, `pytest`, `click` (CLI), Docker buildx multi-arch (x86_64 + ARM64). Licence GPLv3.

**Spec :** `docs/superpowers/specs/2026-11-19-carbon-design.md`

## Global Constraints

- Langage **Python ≥ 3.11** ; accès CAN via **`python-can`** (validé auteur).
- Licence **GPLv3** : fichier `LICENSE` + en-tête SPDX `# SPDX-License-Identifier: GPL-3.0-or-later` en tête de chaque fichier source.
- Image **multi-architecture x86_64 ET ARM64**, même source.
- **Aucun `--privileged` global** : l'accès matériel se fait par `--device`/`--cap-add` ciblé (documenté, pas requis pour le bus `virtual`).
- **Toute action est journalisée** (EF-23, ENF-21) : un adaptateur exécuté sans entrée de journal correspondante est un bug.
- **Action destructrice** (ici : `can_inject`, `can_replay`) = exécutée seulement sur confirmation ; en CLI non interactive, refuser sans `--yes` plutôt que bloquer.
- **Fonctionne sans matériel** : bus `virtual` pour les tests, `vcan0` pour l'intégration (AC-07).
- DRY, YAGNI, TDD, commits fréquents.

## Review Focus

- **Trame CAN invalide** (ID > 0x7FF en standard / > 0x1FFFFFFF en étendu, payload > 8 octets, octet hors 0–255) passée à `can_inject`/`can_replay` → erreur de validation claire, pas de crash ni d'envoi silencieux. → *Task 6*
- **Fichier de capture vide ou corrompu** passé à `can_replay` → erreur explicite nommant la ligne fautive, pas de stack trace. → *Task 6*
- **Bus indisponible** (`vcan0`/`socketcan` absent, interface inconnue) → message d'erreur avec remédiation (« lancez `setup_vcan.sh` » / vérifier le module), pas de stack trace brute. → *Task 5*
- **Action destructrice en CLI non interactive sans `--yes`** (ex : pipe, CI) → refus immédiat avec code de sortie non nul, jamais d'attente bloquante sur stdin. → *Task 7*
- **Échec d'écriture du journal** (chemin non inscriptible, disque plein) → l'action ne doit pas s'exécuter silencieusement non journalisée ; échec visible. → *Task 3*

### Task 6 : Adaptateurs CAN — sniff, dump, replay, inject

**Files:**
- Create: `carbon/tools/__init__.py`, `carbon/tools/can_sniff.py`, `carbon/tools/can_dump.py`, `carbon/tools/can_replay.py`, `carbon/tools/can_inject.py`
- Test: `tests/tools/test_can_tools.py`

**Interfaces:**
- Consumes: `Adapter`, `ToolResult` (Tasks 1-2), couche CAN (Task 5).
- Produces (tous sous-classes d'`Adapter`, `run()` → `ToolResult`) :
  - `CanSniff` (`name="can_sniff"`, non destructif) : `run(channel, interface, count, timeout)` → résumé + `data={"frames": [...]}`.
  - `CanDump` (`name="can_dump"`, non destructif) : capture vers fichier (`candump`-like), chemin dans `artifacts`.
  - `CanReplay` (`name="can_replay"`, **destructif**) : relit un fichier de capture ; **valide chaque trame** et lève `ValueError` sur fichier vide/corrompu en nommant la ligne.
  - `CanInject` (`name="can_inject"`, **destructif**) : envoie une trame forgée ; **valide** `arb_id` (plage standard/étendu), longueur ≤ 8, octets 0–255.
  - Format de capture : réutiliser le format `candump` (compatibilité can-utils) ; une fonction `parse_capture(path) -> list[tuple[int, bytes, bool]]` factorisée.

- [ ] **Step 1 : Écrire les tests qui échouent** — sur bus `virtual` : `test_sniff_returns_sent_frames`, `test_dump_then_replay_roundtrip` (dump d'un trafic, replay réémet à l'identique), `test_inject_invalid_id_raises`, `test_inject_payload_too_long_raises`, `test_replay_empty_file_raises`, `test_replay_corrupt_line_names_line`.
- [ ] **Step 2 : Lancer, vérifier l'échec** — FAIL.
- [ ] **Step 3 : Implémenter** les quatre adaptateurs + `parse_capture`, en déléguant l'I/O bus à Task 5. Validation d'entrée dans `CanInject`/`CanReplay`.
