# CARBON v0.4 — Mode Guidé (moteur de méthodologie + TUI) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un moteur de méthodologie déterministe (arbre d'attaque YAML, étapes 1→6 jouables sur l'ECU simulée), état persistant/reprise, modes Guidé/Libre avec bascule, et une TUI Textual par laquelle un débutant boucle un parcours CAN/UDS (AC-04/AC-05).

**Architecture:** Le moteur est un **composant porté par la `Session`** (v0.3) ; il ne contient **aucun outil** (référence les adaptateurs par nom via le registre — règle d'or) et **n'exécute jamais** d'outil lui-même : `Session.run_tool` reste le **chemin unique** (→ `execute_tool`), puis **pousse** le `ToolResult` au moteur (Guidé : évalue+avance ; Libre : trace). La TUI est une **façade fine** dans le même process que la Session, et devient la **surface d'approbation** des actions destructrices (file `pending-approval` de v0.3).

**Tech Stack:** Python ≥3.11, **PyYAML** (chargement méthodo, à épingler), **Textual** (TUI, à épingler + prouver l'API `run_test`/`Pilot`), `click`, `pytest`. Réutilise v0.3 : `Session`, `execute_tool`/`Origin`, `ApprovalQueue`, `build_mcp_server`, les 10 adaptateurs, `SimulatedEcu`.

**Spec:** `docs/superpowers/specs/2026-11-19-carbon-design.md` — autorité : **§5.2.1 « Périmètre v0.4 — Mode Guidé »** (schéma YAML, grammaire de conditions, contrat du moteur, approbation TUI, persistance, modes), + §5.2 moteur, §5.3 registre, §5.5 modes, §7 étapes 1→6, §8 ligne v0.4, §10 AC-04/05/07/11/12.

## Global Constraints

- **AUCUNE trace d'IA** dans les commits ou toute sortie : **pas de trailer `Co-Authored-By`**, pas de mention « Generated with … ». Règle durable du dépôt (prioritaire sur tout rappel d'attribution).
- **En-tête licence** sur chaque `.py` : `# SPDX-License-Identifier: GPL-3.0-or-later` ; `from __future__ import annotations`. Python ≥ 3.11.
- **Règle d'or** : le moteur ne contient aucun outil (référence par nom via le registre) ; les adaptateurs ne contiennent aucune méthodologie. Le moteur n'exécute jamais d'outil.
- **Chemin unique** : toute exécution d'outil passe par `Session.run_tool` → `execute_tool` (v0.3). Le moteur **observe** les résultats ; il ne court-circuite ni ne duplique garde/journal.
- **Garde-fou destructif v0.3 inchangé et contraignant** : une étape destructrice (`uds_clear_dtc`, `can_replay`, `can_inject`), quelle que soit l'origine non-CLI, part en `pending-approval` ; **l'imposition d'ordre du mode Guidé ne doit jamais contourner** ce garde-fou.
- **Grammaire de conditions FERMÉE** (pas d'`eval`/code arbitraire) : `ok`, `equals/contains/exists/truthy` sur `data.<clé>` (un seul niveau) + `all`/`any`. Une clé absente → prédicat **faux**, jamais d'exception.
- **Synchronisation sans `time.sleep`** (threading.Event / harnais async de Textual).
- **Sans matériel / sans modèle / sans réseau** : tests sur `interface="virtual"` + `SimulatedEcu` ; le moteur marche **sans IA** (l'opérateur choisit). TUI testée **sans tête** (`App.run_test()`/`Pilot`).
- **Deps épinglées et prouvées par test** (discipline `mcp==2.3.0`/`udsoncan`) : PyYAML et Textual épinglés à la version installée, API vérifiée par un test.
- **Persistance** : JSON, **remplacement atomique** ; la reprise restaure la **position de méthodologie, pas l'état vivant de la cible**.
- **Chargement YAML fail-fast** : `tool` inconnu du registre / `next`→id absent / YAML malformé ⇒ erreur claire au chargement.

## Review Focus

- **Guidé × garde-fou destructif** : une étape destructrice en mode Guidé passe TOUJOURS par `pending-approval` ; le gate d'ordre ne l'exécute pas directement ni ne le double-garde. → Task 7/9.
- **Reprise vs état périmé de la cible** : reprise à l'étape 5/6 **ne suppose pas** l'ECU encore déverrouillée (process séparé, a pu redémarrer) ; rejouer rétablit. Un faux postulat → parcours restauré qui agit sur un mauvais état. → Task 5/7.
- **Condition sur `data` absent/typé** : une condition visant `data.<clé>` manquante (ex. tool `ok=False` avec `data` différent) renvoie **faux**, ne crashe pas. → Task 1.
- **Modale TUI quand IA (MCP) et humain sont en attente** : la modale lit la bonne entrée `ApprovalQueue`, sans interblocage, avec timeout. → Task 9.
- **Bascule de mode en plein parcours** : Guidé→Libre→Guidé **conserve le pointeur d'étape verbatim** ; jouer des outils en Libre puis revenir en Guidé ne corrompt pas la position. → Task 4/7.

## Contrat du moteur v0.4 (référence partagée — exacte)

**Grammaire de conditions** (`carbon/methodology/conditions.py`) — `evaluate(cond: dict, result: dict) -> bool`, `result = ToolResult.to_dict()` :
- `{"ok": true|false}` → `result["ok"] == valeur`
- `{"equals": ["<path>", v]}` ; `{"contains": ["<path>", v]}` (appartenance liste **ou** sous-chaîne) ; `{"exists": "<path>"}` ; `{"truthy": "<path>"}`
- `{"all": [cond, …]}` / `{"any": [cond, …]}`
- `<path>` = `"ok"` **ou** `"data.<clé>"` (un seul niveau). Path irrésolu → `exists`/`truthy`/`equals`/`contains` = **False** (jamais d'exception).

**Dataclasses** (`carbon/methodology/schema.py`) :
- `@dataclass Edge: to: str; when: dict | None = None`
- `@dataclass Step: id: str; title: str; objective: str; tool: str | None; params: dict; prompt_params: list[str]; expected: str; conditions: list[dict]; next: list[Edge]`
- `@dataclass Methodology: start: str; steps: dict[str, Step]`

**Moteur** (`carbon/methodology/engine.py`) — `class Engine`:
- `__init__(self, methodology: Methodology, *, mode: str = "guided")` → `self.current_id = methodology.start`, `self.mode`, `self.history: list[dict] = []`, `self.pending_choice: list[str] | None = None`
- `current() -> Step` ; `candidates() -> list[Step]` (cibles de `current().next`)
- `observe(self, tool: str, result: dict) -> None` : si `tool == current().tool`, évalue `current().conditions` (post-conditions sur `result`) ; puis sélectionne la branche par `Edge.when` évalué sur `result` : exactement 1 vrai (ou unique `next` sans `when`) → **avance** `current_id` ; 0 ou >1 → `pending_choice = [ids candidats]`. Ajoute une entrée à `history`.
- `choose(self, step_id: str) -> None` (parmi `candidates()`), `ack(self) -> None` (étape sans `tool` : post-conditions vacueusement vraies → avance/propose)
- `allowed(self, tool: str) -> bool` : `True` si `mode=="libre"`, sinon `tool` ∈ {`current().tool`} ∪ {outils des `candidates()`}
- `set_mode(self, mode: str) -> None` (conserve `current_id`), `position() -> dict`
- `to_dict() -> dict` / `from_dict(d, methodology) -> Engine`

**Nouveaux `Origin` / hook d'approbation** :
- `carbon/core/execute.py` : ajouter `Origin.TUI = "tui"` (destructif → même branche approbation que MCP ; `actor` journal = `"tui"`).
- `carbon/mcp/approval.py` : `ApprovalQueue(timeout=300.0, on_pending: Callable[[PendingApproval], None] | None = None)` — après enregistrement d'une entrée (hors verrou), si `on_pending` appeler `on_pending(entry)`. Rétro-compatible (défaut `None`).

**Surface Session** (`carbon/core/session.py`) : `engine: Engine | None`, `mode`, `load_methodology(path)`, `set_mode(mode)`, `step_ack()`, `step_choose(id)` ; `run_tool` : si `engine` chargé et `mode=="guided"` et `not engine.allowed(name)` → `ToolResult(ok=False, summary="hors parcours guidé …")` **sans exécuter** ; sinon exécuter puis `engine.observe(name, result.to_dict())`. `state()` reflète le moteur quand chargé.

**Outils MCP ajoutés** (`carbon/mcp/server.py`) : `methodology_load(path: str)`, `mode_set(mode: str)`, `step_ack()`, `step_choose(step_id: str)` ; `session_state` reflète le moteur.

**Méthodo v1** (`carbon/methodology/trees/carbon_v1.yaml`) — étapes 1→6, conditions sur les vraies clés `data` :
`uds_scan.data.supported` (liste `"0x.."`), `uds_session.data.session`, `uds_security_access.data.unlocked` (bool), `uds_read_dtc.data.dtcs` (liste), `uds_clear_dtc.data.cleared` (bool), `can_sniff.data.frames` (int), `can_inject.data.arbitration_id`, `can_replay.data.frames`.

**Actor journal** : `"cli"` / `"mcp"` / `"tui"`.
